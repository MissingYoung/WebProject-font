# 核心业务逻辑与功能链条指南 (前端开发专用)

本文档旨在帮助前端开发者快速理解系统的业务模型，理清**行政班**、**教学班**、**课程**、**选课**等核心概念之间的关联逻辑。

---

## 1. 核心概念速览图谱

系统逻辑分为三个层级：**静态基础层** (人与规则)、**动态开课层** (学期排课)、**交互操作层** (选课)。

### 实体关系简述
*   **行政班 (Administrative Class)** = 学生的“行政归属”（如：21级软件1班）。
*   **基本课程 (Course)** = 课程元数据（如：高等数学，不分学期）。
*   **教学班 (TeachingClass)** = 学生实际“上课的班级”（如：张老师周一教的高数A班）。
*   **培养计划 (Program Requirement)** = 规则表（什么专业的学生必须修什么课）。

---

## 2. 详细逻辑链条

### 2.1 静态基础层 (Static Layer)
这部分数据相对固定，定义了“谁”和“规则”。

#### A. 人员与组织
*   **学生 (Student)**
    *   必须归属于一个 **行政班**。
    *   通过行政班，自动关联到 **专业 (Major)** 和 **学院 (Department)**。
*   **行政班 (Administrative Class)** —— **核心枢纽**
    *   **定义**：学生的自然班级，辅导员管理的基本单位。
    *   **与前端的关联**：
        1.  **身份标签**：展示用户信息时，必显字段。
        2.  **数据隔离**：某些通知或选课限制是基于行政班的。
*   **教师 (Teacher)**
    *   归属于学院。他是后续“教学班”的授课主体。

#### B. 课程与规则
*   **基本课程 (Course)**
    *   **定义**：课程库目录。仅定义代码、名称、学分、简介。
    *   *注意*：这里不包含“谁教”、“在哪上”的信息。
*   **培养计划 (ProgramCourseRequirement)**
    *   **逻辑**：制定规则。例如“软件工程专业，大一上学期，必须修读《高等数学》”。
    *   **前端应用**：这是**“推荐课表”**页面的数据源。
    *   **优先级逻辑**：查询必修课时，后端会优先查找**针对该行政班**的特殊计划（如卓越班）；如果没有，再查找**针对该专业**的通用计划。

### 2.2 动态开课层 (Dynamic Offering Layer)
这部分是每个学期变动的数据，将“规则”实例化。

*   **学期 (Semester)**
    *   时间容器（如：2025-2026 秋季）。所有开课都必须绑定学期。
*   **开课 (CourseOffering)**
    *   **逻辑**：`基本课程` + `学期` = `开课任务`。
    *   **含义**：表示“本学期决定开设《高等数学》”。
*   **教学班 (TeachingClass)** —— **选课实体**
    *   **逻辑**：`开课任务` + `教师` + `时间地点` = `教学班`。
    *   **含义**：这是学生选课列表里看到的实际条目（如：**[01] 高等数学 - 张三 - 周一1-2节**）。
    *   **状态**：草稿 -> 已发布 (可由学生选) -> 已满 -> 已关闭。

### 2.3 交互操作层 (Interaction Layer)

*   **选课窗口 (Selection Window)**
    *   **逻辑**：选课的“大门开关”。
    *   **关联行政班**：管理员可设置“9:00开放给一班，10:00开放给二班”。前端在进入选课页面前，需判断当前用户所属行政班是否在有效窗口期内。
*   **选课 (Enrollment)**
    *   **动作**：学生将自己绑定到 **教学班**。
    *   **结果**：生成选课记录，教学班剩余容量 -1。

## 3. 行政班 (Administrative Class) 的特殊作用详解

行政班在系统中不仅是个名字，它串联了多个业务逻辑：

| 业务维度 | 逻辑说明 | 前端场景示例 |
| :--- | :--- | :--- |
| **排课限制** | 教学班可以设定“仅面向特定行政班” (Relation表)。 | 学生搜索课程时，列表会优先置顶标记为“面向本班”的课程，或过滤掉非本班课程。 |
| **自动选课** | 对于大一新生必修课，系统可通过行政班关系，自动将全班学生加入教学班。 | 学生首次登录查看“我的课表”，发现已经有几门课躺在那了（不可退）。 |
| **培养方案** | 可为特定行政班（如实验班）定制特殊的必修课规则。 | 在展示“必修课完成进度”时，需根据班级ID获取精准的课程列表。 |
| **分批选课** | 通过选课窗口控制不同行政班的入场时间。 | 点击“选课”按钮时，提示“当前时间段未对您所在的班级开放”。 |

## 4. 前端开发场景速查

### 场景一：学生去选课
1.  **检查入口**：调用接口检查当前是否有针对我（我的行政班）开放的 **选课窗口**。
2.  **获取列表**：调用 `GET /course-enrollment/available`。
    *   后端会自动根据我的 **培养计划** 标记出哪些是“推荐/必修”。
    *   后端会根据我的 **行政班** 过滤或标记“本班专享”的教学班。
3.  **提交选择**：用户点击某一个 **教学班**，调用 `POST /enroll`。

### 场景二：查看课表/已选
1.  **获取数据**：调用 `GET /course-enrollment/my`。
2.  **展示**：展示的数据主体是 **教学班** (TeachingClass) 的信息（时间、地点、老师）。

### 场景三：管理员排课
1.  **创建教学班**：选择一门课程。
2.  **绑定限制**：管理员勾选“行政班限制”，选择“21级软件1班”。
    *   *后端逻辑*：向 `teaching_class_admin_class_rel` 表插入数据。
    *   *前端逻辑*：提供一个行政班的多选下拉框。

---

## 5. 关键数据流向总结

> **Admin 配置:** `专业` -> `行政班` -> `培养计划` (规则)
> **排课:** `基本课程` -> `开课` -> `教学班` (关联 -> `行政班`)
> **学生操作:** `学生` (属 `行政班`) -> 在 `窗口期` -> 选择 `教学班` -> 生成 `选课记录`

这个文档涵盖了从基础数据结构到用户交互的完整闭环，特别是强调了行政班作为业务逻辑“胶水”的重要性。
